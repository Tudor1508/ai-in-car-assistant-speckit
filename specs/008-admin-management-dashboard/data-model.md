# Data Model: Admin Management Dashboard

**Status**: Describes the implemented Account extension; no vehicle entity change was made.

## Account

Existing account used by public users, the single administrator, and producers.

| Field | Existing/Added | Meaning and constraints |
|---|---|---|
| `id` | Existing | Opaque account identifier; generated by the backend. |
| `name` | Existing | Required, trimmed, 1–120 characters. |
| `email` | Existing | Login identifier; valid email, max 320 characters, entered spelling preserved. |
| `email_normalized` | Existing | Trimmed/case-folded comparison key; unique across all roles. |
| `password_hash` | Existing | One-way password verifier; never returned by any admin response. |
| `role` | Existing | `user`, `producer`, or `admin`. Public registration assigns `user`; admin create assigns `producer`; the separate trusted provisioner creates the single admin. |
| `status` | Existing | `active` or `disabled`. Disabled accounts cannot authenticate. Admin user deletion changes `active` to `disabled`. |
| `created_at`, `updated_at` | Existing | Server-assigned timestamps used for dashboard display/filter/sort. |
| `brand` | Added, nullable | Required trimmed free text, at most 120 characters on new producer creation, matching the API schema and model; null for users/admins and legacy producers with no supplied brand. Included in safe producer DTO only. |
| `admin_slot` | Added, nullable | Fixed singleton value for role `admin`; null for other roles. Unique constraint limits the database to one row with the admin slot. A check constraint keeps role and slot consistent. Never exposed through API. |

### Account validation and role transitions

- Producer create accepts non-empty name, brand, valid email, and password. Reuse current account name/email/password validation, email normalization, uniqueness, and `hash_password` behavior.
- Producer passwords must be at least 8 characters with one uppercase letter, one number, and one special character.
- Public registration remains fixed to `role=user`; client role input is already forbidden and does not change.
- Admin provisioning claims the singleton slot only if unoccupied. Trusted role changes assign/clear the slot along with role changes; database uniqueness is the final guard.
- An admin dashboard deactivation targets only `role=user`; it preserves the account row, sets status disabled, updates its timestamp, and revokes active sessions.
- No producer edit/deactivate action or administrator deletion is in this feature.

## Vehicle

Existing entity; no schema changes in this feature.

| Field | Use in admin view |
|---|---|
| `id` | Stable row identity; not a user-facing filter. |
| `owner_account_id` | Used only for joins if required; not returned in the dashboard DTO. |
| `name`, `model` | Displayed and filterable/sortable text fields. |
| `type` | `combustion` or `electric`; displayed, filterable/sortable, and used for counts. |
| `year` | Displayed, filterable, and sortable. |
| `range_km`, `mileage_km` | Displayed, filterable, and sortable numeric kilometer values. |
| `fuel_type` | Existing enum or null; displayed, filterable, and sortable. |
| `created_at` | Displayed and sortable timestamp. |
| `updated_at` | Available record timestamp; may be returned only if the existing UI needs it. |

Admin reads all vehicles; normal `/vehicles` stays owner-scoped. No admin create/update/delete operation is added.

## Dashboard Aggregates

These are derived read models, not persisted entities:

- **Users**: all total plus active and disabled counts for records with role `user`.
- **Vehicles**: all total plus combustion and electric counts.
- **Producers**: all total plus counts grouped by brand. Legacy null brand maps to a distinct unassigned bucket.

Counts describe the full section independently of current table filters/sorting. Successful user deactivation updates user status counts; successful producer creation updates producer total and brand count.

## Relationships and Data Retention

- `Vehicle.owner_account_id` and trip favorites reference Account with existing cascade behavior on physical deletion.
- This feature deactivates user accounts instead of deleting them; existing vehicles/favorites remain attached and unchanged.
- Password verifiers, session/token material, and internal admin-slot values are excluded from list, statistics, and mutation response models.
